Why Microservices? (Monolith vs. Microservices)

Modular Architecture for High Availability and Scalability

Slide Bullet Points

  • Monolithic Risks: Single failure point—if messaging or media crashes, the entire platform goes down.
  • Decoupled Services: Identity, Post Creation, Newsfeed, Follower Graph, and Messaging operate independently.
  • Fault Tolerance & Scaling: Heavy video streaming does not bottleneck database operations or user authentication.

🗣️ Word-for-Word Speaker Notes

"In traditional monolithic web applications, tightly coupled features create a single point of failure. In our architecture, we decoupled key domain boundaries: Identity & Profiles, Cloud Media Storage, Feed Generation, the Relational Social Graph, and Real-Time Messaging. This design ensures modular maintenance, fault tolerance, and independent scalability."

Service 2: Post Creation & Media Storage

Direct Cloud Storage Pipeline & Relational Linking

Slide Bullet Points

  • Direct-to-Bucket Pipeline: High-res images upload to Supabase Storage (instagram-bucket) with unique timestamped hashes.
  • Lightweight Database: PostgreSQL stores only the public CDN image URL and post metadata.
  • Instant Feed Notification: Global event dispatches immediately upon post creation to trigger zero-lag feed updates.

🗣️ Word-for-Word Speaker Notes

"Our second service is Post Creation and Media Storage. Storing heavy images in a standard database bottlenecks performance. Our upload pipeline streams images directly into an S3-compatible cloud storage bucket, storing only the optimized public CDN URL in PostgreSQL. Once published, an event immediately signals the feed to refresh."

Service 4: Relational Social Graphs

Complex Follower-Following Mapping with Instant State Sync

Slide Bullet Points

  • Directional Graph: Relational followers table linking follower_id to following_id.
  • Instant State Sync: Optimistic UI updates toggle buttons between Follow and Unfollow with immediate counter adjustment.
  • Dynamic Suggested Users: Homepage sidebar queries real non-followed users directly from PostgreSQL.

🗣️ Word-for-Word Speaker Notes

"The fourth service is our Relational Social Graph. Unlike symmetric friendship models, Instagram uses a directional graph: User A can follow User B without User B following back. We implemented this using a relational followers table with instant state synchronization, allowing one-click follow and unfollow toggling across the home feed and profiles."

Service 5: Real-Time Events & Direct Messaging

Sub-100ms Bi-directional Messaging Replacing HTTP Polling

Slide Bullet Points

  • WebSockets over Polling: Eliminates continuous server requests; maintains a persistent two-way socket tunnel.
  • PostgreSQL WAL Integration: Database Write-Ahead Logs trigger instant message broadcasting.
  • Sub-100ms Latency: New messages appear on recipient screens in under a tenth of a second without page reloads.

🗣️ Word-for-Word Speaker Notes

"Our fifth service is Real-Time Direct Messaging. Traditionally, web applications relied on HTTP polling—repeatedly asking the server every two seconds for updates. We replaced polling with persistent bi-directional WebSockets via Supabase Realtime. When a user sends a message, PostgreSQL broadcasts the write event immediately, delivering messages to the recipient's screen in under 100 milliseconds."

Database Architecture & Row Level Security (RLS)

PostgreSQL Relational Schema & Engine-Level Privacy

PostgreSQL Relational Tables

  • users, posts, comments, likes, followers, conversations, messages.
  • Database-Level Security (RLS): SQL policies enforce data privacy directly at the database engine level (e.g. users can only read messages where auth.uid() = sender_id OR auth.uid() = recipient_id).

🗣️ Word-for-Word Speaker Notes

"Security is handled directly at the database layer using PostgreSQL Row Level Security. Rather than trusting client code, every database query verifies auth.uid() at the database engine level. This guarantees that private messages and conversations cannot be accessed by unauthorized users."

Engineering Challenges Overcome

Real-World Problem Solving & Architecture Decisions

Key Engineering Solutions

  • Firebase to Supabase Migration: Converted unstructured NoSQL documents into structured relational PostgreSQL schemas with foreign key integrity.
  • Browser Autoplay Restrictions: Synchronized DOM mute properties with React state to comply with strict Chrome/Edge autoplay policies.
  • Vercel SPA 404 Resolution: Implemented vercel.json rewrites to ensure deep routing (/explore, /reels, /:username) never 404s on page refresh.

🗣️ Word-for-Word Speaker Notes

"Building this project gave me hands-on experience solving complex edge cases: migrating from Firebase NoSQL to PostgreSQL, overcoming browser autoplay security sandbox restrictions, and configuring edge routing rules on Vercel to support deep Single Page Application links."
